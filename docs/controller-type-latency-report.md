# Controller 类型热更新延迟优化

用户反馈保存路由后的自动类型更新体感过慢。沿保存监听、TypeScript 分析、声明写入链路完成两轮优化，保持现有路由声明与独立 Controller 写法。

## 第二轮：按变更检查与有界缓存

开发服务不再让每个保存事件都扫描工程、调用 TypeScript 生成器。只读取本批变更文件，更新其内容指纹；重复保存直接返回，恢复已完整验证的输入版本则直接更新声明。缓存命中立即处理，不等待 30 ms 的事件合并窗口。首次出现的输入、配置变化、文件增删或依赖集合变化仍进入 TypeScript 分析。

本机 Node v24.21.0，完整 React 模板，两轮独立测量。重复保存、缓存回放和全新 schema 分开计时；全新 schema 每次新增不同的 query 字段，不能靠交替两个旧版本命中缓存。

| 路径                                   | 样本数 | 中位耗时     |
| -------------------------------------- | ------ | ------------ |
| 重复保存，内容未变                     | 64     | **41 μs**    |
| 恢复已验证的路由版本，包含声明文件写入 | 30     | **119 μs**   |
| 每次引入不同的新 schema，需要重新推导  | 32     | **124.8 ms** |

微秒数据是变更处理函数耗时，包含读取变更文件、指纹比较，以及需要时写入声明；不包含操作系统投递文件事件、Vite 排队或编辑器语言服务/UI 更新。没有宣称任意新类型推导都已达到微秒级。

真实公开 `/vite` 入口的两轮连续保存测试，中位延迟分别为 **2.0 ms** 和 **1.54 ms**，以 1 ms 轮询观察生成声明。第二轮样本为 129.709、1.216、1.556、1.469、1.540、1.543 ms；首个新类型需要推导，其后复用已验证版本。第一轮另有一次 83 ms 抖动，因此不是每次保存的时延保证。params/query 类型错误检查及无重复写入循环均通过。只使用父目录事件的中间版本为 43 ms，应用源码改用直接文件事件后显著降低了事件投递等待。

缓存以整个已读输入集合的内容指纹为依据，包括 Controller、路由、导入的 schema、配置及包元数据。版本缓存复用框架已有 `LruMap`，最多保留 8 个版本；不会新增第二份类型推导器。未注册 Controller 的契约依赖历史状态，遇到这种情况清空版本缓存，继续保留其最后已知契约。

应用源码使用 TypeScript 原生文件事件，减少目录事件批处理的延迟；依赖共用父目录监听，覆盖 Vite 默认忽略的 `node_modules`、外部与仅类型依赖。外部输入目录及父目录监听覆盖新增声明替换旧模块的情况。订阅随依赖集合更新，服务关闭时取消任务、关闭全部文件/目录订阅并释放分析和版本缓存。配置和新增、删除文件触发失效；缓存回放也执行生成文件所有权及真实路径检查。

需要推导时，三阶段共享单次生成的磁盘读取和模块解析结果；每次新分析重新检查依赖，保留 import/require 的不同解析模式。引入版本缓存前的交替对照中，生成耗时中位数从 191.8 ms 降至 124.8 ms，模块解析阶段从约 61.4 ms 降至 17.0 ms。保留语法检查、声明语义校验、格式化幂等和连续保存保护。

新增回归先复现了两个缓存问题，再验证修复：只修改包的 `exports` 未刷新，以及在依赖目录新增 `index.ts` 后仍沿用旧 `index.d.ts`。还覆盖相同时间戳的内容变化、多文件连续保存、删除生成声明后的恢复、未注册契约、非托管输出和输出悬空符号链接。

48 次更新（包含 24 个不同新 schema）、每次显式 GC 的有限观测：堆占用从 208.6 MiB 到 224.1 MiB，最高 224.2 MiB；关闭缓存后 28.5 MiB。这是分析与版本缓存的进程内存记录，不代表生产运行时或无限运行的内存保证。

验证：`vp check --fix`、929 项测试、21 个构建任务通过；生成器专项共 31 项，包括异步关闭开始后立即停用类型监听。独立只读复核未发现 Important/Critical 问题。

证据目录：`reports/controller-type-latency-next/`。其中 `before-final-{a,b}.json` 与 `after-final-{a,b}.json` 是生成器交替对照；`watch-cache-final-{a,b}.json` 分别记录缓存与全新 schema；`watch-cache-direct{,-b}/native-flow.json` 记录真实监听；`watch-cache-memory.json` 记录内存；`resolution-before.log` 和 `dependency-add-{before,after}.log` 保留失效问题的复现。

复测缓存路径与全新 schema：

```bash
vp exec node scripts/measure-controller-types.mjs packages/server/src/controller-types.ts reports/controller-type-latency-next/recheck.json 16 watch
```

## 第一轮测量结果（历史记录）

本机 Node v24.21.0；使用临时项目副本，不修改正在使用的应用。完整 React 模板采用优化前、优化后交替运行两轮，每轮连续修改路由 8 次；分别断言生成的数字、字符串类型正确，未变化的输入不产生写入。

| 场景                                             | 优化前       | 优化后     |
| ------------------------------------------------ | ------------ | ---------- |
| 完整 React 模板，16 次路由更新的生成耗时中位数   | 978.1 ms     | 189.3 ms   |
| 同一模板首次生成，两轮观测范围                   | 1230–1266 ms | 645–651 ms |
| 真实 Vite 开发服务，6 次保存到声明更新的中位延迟 | 1052 ms      | 192 ms     |

真实监听链路的 6 次优化后样本为 307、293、189、184、195、170 ms，中位延迟减少约 82%。这是从文件保存到生成声明可读取的延迟；编辑器展示补全或诊断还包含自身语言服务的刷新时间，本次未测量编辑器 UI 延迟。

## 原因与修改

- 原实现每次有效保存重新创建三份完整 TypeScript 分析。最初完整模板样本的解析阶段约 500 ms、绑定阶段约 220 ms，构成主要开销。现在复用前一份 Program 和内容未变化的 SourceFile，同时重新解析模块依赖，保留配置及导入变化的更新能力。
- 原始、推导和校验三个阶段使用同一个分析构建函数；保留语法检查、生成声明的语义校验、源码所有权检查和幂等写入。
- 仅在字段使用对象或交叉类型 schema 时扫描可访问的 schema 导出，避免普通字符串、数字参数也遍历全部依赖导出。名义类型及未导出类的 schema 引用继续保留。
- 保存事件合并等待从 100 ms 调整为 30 ms，短时间内的多次保存仍合并处理。
- 复现并修复连续保存的缓存问题：若生成期间又保存了路由，不能用结束时的新时间戳标记旧分析结果。缓存现在记录分析所读输入的时间戳，后续保存会重新生成。

编译分析缓存只保留最近一个应用，服务关闭时释放。构建新 Program 后也清除 host 对上一份 Program 的引用，避免形成保留历史分析的引用链。

这是开发工具的时间与内存取舍。连续 24 次更新、每次显式 GC 后，进程堆占用从 213.8 MiB 到 219.7 MiB；释放分析缓存后为 28.0 MiB。此记录包含 TypeScript 与测试项目，属于有限次数的本地观测，不是生产运行时性能指标。
